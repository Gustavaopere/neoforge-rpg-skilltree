# Integration Plan — Create Rock & Stone (RNS)

**Goal:** expose Volcanoes hydrothermal/magmatic deposits to the existing prospecting gameplay without deleting or duplicating RNS ore generation.

- [x] Inspect installed RNS datapack/KubeJS/API extension points and choose the least invasive supported path.
- [x] Implement deterministic projection support for `GeologicalDeposit` entries that already carry an exact supported `c:ores/<metal>` identity.
- [x] Do not add a Volcanoes scanner if RNS is installed.
- [x] Keep projection lifecycle stable and idempotent across add/remove/reload/restart paths.
- [x] Keep adapter absence/version mismatch fail-soft.
- [x] Establish a canonical production contract that emits exact per-metal identities for Volcanoes-generated hydrothermal deposits when volcanic causality is proven.
- [x] Physically generate the corresponding Stage 01 ore family for every exact identity Volcanoes currently intends to own (`copper`, `iron`, `gold`).
- [x] Resolve RNS native-worldgen ownership semantics: retain native RNS worldgen because globally disabling an RNS metal family is not semantically equivalent to replacing only bounded Volcanoes hydrothermal bodies.
- [x] Enable the production RNS lifecycle bridge under an exact-host coexistence contract limited to the physically covered Cu/Fe/Au projection families.
- [x] Persist Volcanoes ownership proof in the exact RNS custom-location host record so restart recovery cannot adopt or remove a foreign same-value projection.

**Acceptance:** prospecting stays centralized in RNS while Volcanoes adds geologically meaningful deposit origins, with no RNS ore family removed, no second ore body generated by the projection bridge and no destructive action against an RNS custom location whose Volcanoes ownership is not durably proven.

## Canonical state — physical Cu/Fe/Au plus RNS prospecting coexistence

`HydrothermalDepositProjector`, the production deposit producer used by `GeothermalWorldgenRuntime`, asks the deterministic `GeothermalWorldgenResolver` for the volcano whose magma contribution actually raises geothermal potential above the tectonic baseline. `HydrothermalMineralizationPolicy` then assigns only the Stage 01 metal families recognized by the core geology contract:

- shield / fissure → `c:ores/iron`;
- stratovolcano → `c:ores/copper`;
- caldera → `c:ores/gold`;
- no proven volcanic cause → `volcanoes:resources/mineral`.

The classification is deterministic from world seed and position. Tin, nickel, zinc and silver are not produced by Volcanoes and remain outside its RNS projection scope.

`GeothermalWorldgenFeature` projects the same deterministic `GeologicalDeposit`, asks `HydrothermalOreWorldgenProducer` for a bounded placement plan, and materializes the matching vanilla ore family only into natural stone/deepslate ore-replaceable hosts. Preparation requires the complete bounded target before mutation; application revalidates expected hosts before writing and rolls back prior writes if a write fails.

A successful physical application is carried as `hydrothermalDepositPhysicallyRealized` through `GeothermalChunkHandoff` and `GeothermalWorldgenRuntime`. Exact Cu/Fe/Au metadata is inadmissible without that proof. Legacy exact metadata lacking proof is revoked during reconciliation when it matches the expected Volcanoes projection, while mismatched registry content remains fail-closed.

## Why native RNS worldgen remains enabled

RNS KubeJS selection operates on complete RNS deposit families. Volcanoes does not provide a one-for-one replacement for every native RNS copper, iron or gold structure; it only creates bounded hydrothermal bodies at its own geothermal expressions. Globally disabling `deposit_copper`, `deposit_iron` or `deposit_gold` would therefore remove unrelated RNS deposits and would violate the integration goal.

The canonical startup template consequently keeps every RNS deposit enabled. This is not deferred ownership: it is the final coexistence contract.

`RnsCompat.projectedDepositIds()` contains only:

- `create_rns:deposit_copper`;
- `create_rns:deposit_iron`;
- `create_rns:deposit_gold`.

`RnsDepositProjectionPlanner` mirrors that same physical authority boundary and rejects exact tin, nickel, zinc and silver metadata instead of publishing those families as Volcanoes custom RNS locations.

`RnsCompat.projectionReady(...)` requires the exact RNS/KubeJS host to be managing deposits and requires all three projected IDs to remain selected/scannable. As an independent coexistence safety gate, native RNS worldgen must remain enabled for all seven protected metal families: copper, iron, gold, tin, nickel, zinc and silver. Removing any protected native family makes the adapter fail closed.

Tin, nickel, zinc and silver therefore remain entirely RNS-native: they are required to keep native worldgen, but they are excluded from the Volcanoes projection set and from `RnsDepositProjectionPlanner`.

## Prospecting projection does not duplicate ore generation

`RnsHostDepositProjectionWriter` uses the exact host API `LevelDepositData.addCustomDeposit(...)` / `removeCustomDeposit(...)` with `CustomServerDepositLocation`. It contributes RNS custom deposit locations for prospecting; it does not place ore blocks and does not invoke RNS structure generation.

The lifecycle is therefore:

1. Volcanoes physically realizes a bounded hydrothermal Cu/Fe/Au body;
2. only physically authoritative exact metadata enters `DepositRegistry`;
3. `RnsDepositLifecycleBridge` observes the authoritative registry snapshot;
4. `RnsHostDepositProjectionWriter` creates the matching RNS custom/scannable location and attaches the authoritative Volcanoes source UUID marker to that exact host record;
5. native RNS deposit structures continue to generate under RNS authority;
6. removing the Volcanoes deposit removes only a matching owner-marked custom RNS prospecting projection.

This separates physical generation authority from prospecting metadata and avoids both unsafe global deletion and a second generated ore body.

## Ownership safety across restart

Create: RNS `1.3.1-1.21.1-6` natively serializes a custom location by deposit id and location only. Those value fields cannot prove that a same-value record observed after restart is the object originally inserted by Volcanoes. An external side ledger is therefore insufficient as destructive authority.

PR #84 hardens the exact supported host with a narrow compatibility Mixin: a Volcanoes-created `CustomServerDepositLocation` carries `volcanoes_owner_source_id`, the authoritative source UUID, through the host record's own `serialize()` / `of(...)` persistence path. `RnsProjectionOwnershipData` remains auxiliary state only. Rebind or removal requires the matching host-local source marker plus the expected precise projection identity; a foreign record recreated at the same deposit id/chunk/center has no marker and fails closed.

The exact-host regression suite forces the real `LevelDepositData.serializeNBT(...) -> deserializeNBT(...)` round-trip, proving that ownership survives host reconstruction without restoring authority from value equality.

## Exact-host acceptance

The pinned integration remains:

- Create: Rock & Stone `1.3.1-1.21.1-6`;
- KubeJS `2101.7.2-build.368`.

Dedicated NeoForge GameTests verify that:

- Cu/Fe/Au remain selected for Volcanoes custom prospecting projection;
- Cu/Fe/Au/Sn/Ni/Zn/Ag all retain native RNS worldgen;
- the coexistence readiness predicate activates on the exact supported host only while those native-worldgen invariants hold;
- registering an authoritative exact hydrothermal deposit creates exactly one matching RNS custom location;
- removing that authoritative deposit removes the custom location only when Volcanoes ownership is proven;
- pre-existing and same-value foreign custom locations are not adopted or deleted;
- the owner UUID survives a real RNS NBT serialize/deserialize cycle and permits legitimate restart rebind/removal;
- optional-host absence/version mismatch remains fail-soft;
- bounded retry and level-unload teardown remain in production.

The startup template deliberately leaves every `.deposit(..., true)` unchanged and does not override RNS frequency-pack spacing, separation or salt.

## Closure

The Stage 06 RNS integration is complete under coexistence rather than global worldgen transfer. Volcanoes owns the physical hydrothermal bodies it actually generates and its explicitly owner-marked custom prospecting records; RNS owns its native worldgen and remains the unified prospecting surface. No protected RNS metal family is removed from native worldgen, and Volcanoes publishes custom prospecting locations only for its physically proven Cu/Fe/Au families.
